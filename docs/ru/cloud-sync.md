# Облачная синхронизация

Как **Sync** (синхронизация) приводит локальное хранилище (vault) и облачную копию в соответствие друг с другом. Формат файла и правила слияния описаны в [vault.md](vault.md).

Код:

- `Erapkey.Core/Services/SyncService.cs` — цикл синхронизации (`Synchronize`).
- `Erapkey.Core/Services/CredentialsCryptoService.cs` — `MergeFromCloud` (слияние и выбор ключа хранилища и мастер-пароля) и `MergeVaults` (чистое слияние).
- `Erapkey.Core/Clouds/Services/` — провайдеры: `Download`, `GetRevision`, `Upload`.
- `Erapkey/ViewModels/CloudSyncViewModel.cs` — кнопка, запрос пароля и диалог с результатом.

## Кратко

Синхронизация = **загрузка → слияние → отправка при необходимости**, с проверкой ревизии перед отправкой. Отдельной отправки нет: её убрали, потому что она вслепую перезаписывала облачную копию.

## Шаги

Каждая попытка:

1. **Загрузка** `erapkey.dat`. Запомнить его MD5 как *ожидаемую ревизию*. Файла в облаке нет — перейти к шагу 4.
2. **Расшифровка.** Если облачный файл использует ключ хранилища этого устройства (тот же id ключа), он расшифровывается этим ключом: без пароля и без Argon2. Это обычный случай. Иначе пробуется пароль, введённый в предыдущей попытке, затем пароль, сохранённый для первой синхронизации после создания или преобразования хранилища при этой разблокировке (см. ниже), затем пользователя спрашивают, пока пароль не подойдёт или пользователь не отменит (отмена = синхронизация не удалась, ничего не отправлено). Облачный файл, записанный более новым Erapkey, сразу приводит к ошибке синхронизации с сообщением «обновите Erapkey».
3. **Слияние** в локальное хранилище и запись локального файла. Если слияние что-то меняет, сначала делается резервная копия локального хранилища типа `sync` (см. [vault.md](vault.md#backups)). Удаления (надгробия, tombstones) применяются здесь, поэтому удалённые учётные данные не возвращаются. Если облачный файл использует другой ключ хранилища, см. [Ключ хранилища и мастер-пароль](#vault-key-and-master-password).
4. **Решение, нужна ли отправка.** Отправка нужна, когда:
   - в облаке нет файла;
   - слияние локального хранилища в загруженное изменило бы его (в облаке чего-то не хватает: новые или изменённые учётные данные, удаление, изменение группы, более новая метка времени пароля);
   - облачный файл использует другой ключ хранилища, чем локальный (он перешифровывается ключом этого устройства);
   - облачный файл в формате 1 или в устаревшем формате.

   Иначе синхронизация заканчивается: ничего не отправляется.
5. **Проверка ревизии.** Прочитать локальный файл, запросить у провайдера текущий MD5 облачного файла. Отличается от ожидаемой ревизии (или файл появился/исчез) → за это время другое устройство выполнило отправку → начать следующую попытку с шага 1.
6. **Отправка** локального файла как есть.

Не более **3 попыток**. Если в каждой попытке ревизия оказывается изменённой, синхронизация завершается ошибкой «The cloud copy kept changing during synchronization». Всё, что было слито в предыдущих попытках, остаётся в локальном хранилище.

```
download ─► decrypt ─► merge (local file written)
                            │
                  cloud up to date? ── yes ─► done
                            │ no
                  revision unchanged? ── no ─► next attempt (max 3)
                            │ yes
                          upload ─► done
```

<a id="vault-key-and-master-password"></a>
## Ключ хранилища и мастер-пароль

Все устройства одного хранилища должны использовать один ключ хранилища (vault key) (см. [vault.md](vault.md#keys)); тогда синхронизации не нужны ни пароль, ни Argon2. Ключ передаётся внутри облачного файла, в его слоте пароля (password slot). Облачный файл с другим ключом появляется, когда:

- мастер-пароль был изменён на другом устройстве (смена создаёт новый ключ);
- устройства независимо преобразовали свои файлы Erapkey 1.x, и каждое получило свой случайный ключ;
- на этом устройстве было создано новое хранилище, пока в облаке уже было другое.

Хранилище содержит `MasterPasswordChangedAt` (задаётся при смене пароля; неизвестно = самое старое). Для открытия такого облачного файла нужен его пароль, и далее:

| Облачный файл | Ситуация | Результат |
|---|---|---|
| Формат 2, другой ключ | Облачный пароль изменён позже или одновременно (включая оба неизвестных), и у облачного ключа меньший id ключа | Это устройство берёт облачный ключ и слот и перешифровывает свой файл ими (сначала резервная копия `sync`; резервная копия `password`, если пароль отличается). Если облачный пароль отличается от локального, пользователю сообщается, что мастер-пароль изменён на другом устройстве. |
| Формат 2, другой ключ | Локальный пароль изменён позже или одновременно, и у локального ключа меньший id ключа | Локальный файл сохраняет свой ключ; облачная копия отправляется с ним. |
| Формат 1 или устаревший | Облачный пароль изменён позже и отличается | Это устройство переходит на облачный пароль с новым ключом (пользователю сообщается). |
| Формат 1 или устаревший | Иначе | Локальный файл сохраняет свой ключ; облачная копия отправляется в формате 2 с ним. |

При равенстве выигрывает меньший id ключа. Правило не зависит от того, какая сторона — облако, поэтому каждое устройство и каждое облако (Google Drive и Yandex Disk могут начинать с разными ключами) приходят к одному и тому же ключу; если бы вместо этого выигрывало облако, устройство, синхронизирующее два облака, переключалось бы туда-обратно при каждой синхронизации. Для облачных файлов 1.x при равенстве сохраняется локальный пароль, как и раньше; после отправки облачный файл в любом случае окажется в формате 2. Таким образом, смена пароля на одном устройстве доходит до облака и других устройств, а не откатывается.

Пароль спрашивается только пока облако использует другой ключ: не чаще одного раза на устройство и облако, пока ключи не совпадут. Чтобы не задавать этот вопрос сразу после ввода пароля, разблокировка, которая создаёт хранилище или преобразует файл 1.x, держит мастер-пароль в памяти до блокировки хранилища (`CredentialsCryptoService.FirstSyncPassword`), и синхронизация пробует его. Он забывается раньше, если пароль меняется — здесь или при принятии облачного. Другие разблокировки сохраняют только ключ хранилища.

## Провайдеры

| | Google Drive | Yandex Disk |
|---|---|---|
| Область доступа (scope) | `drive.file` (только файлы, созданные этим приложением) | `cloud_api:disk.app_folder` |
| Файл | Самый старый не удалённый в корзину файл с именем `erapkey.dat` | `app:/erapkey.dat` |
| Ревизия | `md5Checksum` | `md5` ресурса |
| Создание | Один multipart-запрос (метаданные + содержимое) | Ссылка для загрузки с `overwrite=true` |

## Прогресс, показываемый пользователю

Пока идёт синхронизация, карточка аккаунта показывает индикатор прогресса и текущий этап из `SyncService.SyncStateChanged(cloudType, text)`: загрузка, расшифровка, слияние, отправка или «облачная копия изменилась, синхронизация повторяется», когда попытка повторяется. Пустой текст означает, что синхронизация завершилась.

После успешной синхронизации карточка также показывает **Last sync** (локальные дата и время). Оно хранится отдельно для каждого облака в `commonSettings.json` (`LastSyncTimes`, UTC), поэтому описывает только это устройство, и очищается при выходе из аккаунта.

## Результат, показываемый пользователю

Новые, изменённые и удалённые учётные данные; «группы обновлены»; «мастер-пароль изменён на другом устройстве»; «облачная копия обновлена» или «облачная копия обновлена и перешифрована паролем этого устройства»; либо «изменений нет».

## Практические правила

- Одновременно выполняется только одна синхронизация на провайдера; пока она идёт, интерфейс блокирует другие передачи.
- Блокировка хранилища отменяет синхронизацию.
- Локальные правки во время синхронизации безопасны: при отправке уходит текущий локальный файл, который их включает.
- Запрос пароля выполняется в потоке пользовательского интерфейса, поэтому `Synchronize` сохраняет контекст вызывающего (там нет `ConfigureAwait(false)`).

<a id="known-limitations"></a>
## Известные ограничения

- **Проверка ревизии не атомарна.** Ни у Google Drive v3, ни у Yandex Disk нет условной записи, поэтому шаги 5–6 — это «проверить, затем записать». Отправка с другого устройства в короткий промежуток между ними будет перезаписана. У того устройства данные всё ещё есть локально, и оно вернёт их при следующей синхронизации, так что данные теряются, только если это локальное хранилище будет потеряно раньше.
- **Метки времени берутся из часов устройств.** Конфликты учётных данных, «правка против удаления» и смена мастер-пароля используют их; расхождение часов может привести к выбору неверного победителя.
- **Принудительной перезаписи нет.** Если облачное хранилище не удаётся расшифровать (забытый пароль, повреждённый файл), синхронизация не может продолжиться; удалите облачный файл вручную.
- **Erapkey 1.x не читает формат 2.** Как только одно устройство выполнило отправку, устройства, остающиеся на 1.x, продолжают запрашивать пароль облачной копии; они его не меняют. Обновите все устройства.
